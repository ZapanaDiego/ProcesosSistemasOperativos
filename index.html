El concepto en 60 segundos

La memoria compartida POSIX es la forma más rápida de comunicar procesos porque no copia datos: ambos procesos.Acceden a la misma página física de RAM. Cuando el productor escribe, el consumidor lo ve al instante.

📦

producer.c — el escritor

Crea el objeto de memoria compartida, le reserva 4096 bytes, lo mapea en su propio espacio de direcciones y escribe las cadenas "Hello" y "World!" dentro.

📖

consumidor.c — el lector

Abre el mismo objeto solo lectura, lo mapea, imprime lo que encuentra y finalmente destruye el objeto con shm_unlink.

⚡

El tradeoff

Cero overhead de copia, pero sin sincronización gratis: si los dos tocan la memoria a la vez, tenés una carrera de datos.

Anatomía mental: shm_open crea un archivo especial en /dev/shm/ (RAM disfrazada de filesystem). mmap genera un mapeo: un rango de direcciones virtuales de tu proceso conectado a ese archivo. Mapeás el archivo → las dos partes comparten la misma página física.

El mmap en una imagen

ptr = mmap(  0,              // dirección 0 = "elegí la que quieras"
              4096,            // longitud en bytes
              PROT_WRITE,      // permisos: solo escritura
              MAP_SHARED,      // los cambios van al objeto compartido
              fd,              // el descriptor que devolvió shm_open
              0 );             // offset dentro del objeto

El argumento que más importa es MAP_SHARED. Si puseras MAP_PRIVATE, el kernel haría copy-on-write: el consumidor leería una copia paralela y jamás vería lo que escribió el productor.

    Lo que este visualizador no muestra: la sincronización. En el código real no hay ningún semáforo ni lock, así que el consumidor puede leerse antes de que el productor escriba. Abajo, en Carrera de datos, simulamos qué pasa.
  






  
Carrera de datos: el bug invisible

  
El productor tarda unos microsegundos entre crear el objeto y escribir. Si el consumidor arranca durante esa ventana, lee memoria vacía o partially written. Vamos a medir cuán seguido pasa.


  

    
Simulador Monte Carlo · 2000 corridas

    
Modelo: el productor crea el objeto en t≈0.2 ms, escribe "Hello" en t≈1.0 ms y "World!" en t≈2.0 ms. El consumidor arranca en un instante aleatorio uniforme entre 0 y 4 ms.

    

      
      
    

    

    

  


  

    

      ❌ Lo que pasa ahora

      Sin barreras, el resultado es no determinista. En una Shell parece "siempre funciona" porque el productor arranca antes — eso es azar de arranque, no corrección.
    

    

      ✅ La solución clásica

      Un sem_t POSIX. El productor hace sem_post al terminar de escribir; el consumidor hace sem_wait antes de leer.
    

    

      ⚠️ La trampa

      Si compartís el semáforo dentro de la misma memoria compartida, protegés el semáforo con la memoria que el semáforo protege. Va en un objeto aparte.

Qué hace exactamente cada llamada

  
Las cinco funciones que aparecen en el código, explicadas con su firma, su efecto real en el kernel y sus errores típicos.


  

    1 · shm_open int shm_open(const char *name, int oflag, mode_t mode)
    

      
Es un open(2) para objetos de memoria compartida. Bajo el hood es el mismo archivo que tenés en /dev/shm (tmpfs: un filesystem que vive en RAM).

      
fd = shm_open( "OS",             // nombre, se prefija con /
             O_CREAT | O_RDWR,  // flags
             0666 );           // permisos, solo si crea

      
    
        
  • O_CREAT — crea el objeto si no existe. Es lo que usa el productor. Devuelve el error EEXIST si ya existía… salvo que sumes O_EXCL.
    • 
        
  • O_EXCL — usado junto a O_CREAT, obliga a fallar si ya existe. Evita que otro proceso pise los datos.
    • 
        
  • O_RDWR — el productor necesita leer y escribir en el mapeo.
    • 
        
  • O_RDONLY — el consumidor mapea PROT_READ, así que solo necesita lectura.
    • 
        
  • mode (0666) solo se aplica en la creación. 0666 es un error tipográfico: & ejecutalo con umask.
    • 
      

      
Error clave: si el consumidor corre antes que el productor y usa O_CREAT, crearía un objeto vacío y leería basura. Por eso el consumidor usa O_RDONLY sin O_CREAT → falla con ENOENT y el perror avisa.

    

  


  

    2 · ftruncate int ftruncate(int fd, off_t length)
    

      
Fija el tamaño del objeto. Obligatorio, y es el paso que casi todo el mundo olvida.

      
ftruncate( fd, 4096 );   // 1 página exacta de memoria

      
    
        
  • Un objeto recién creado con shm_open mide 0 bytes.
    • 
        
  • mmap con longitud 0 falla con EINVAL. No podés mapear cero bytes.
    • 
        
  • Al extender a 4096 bytes el kernel reserva una página real, y esa página entra ceroizada.
    • 
      

      
Consecuencia directa: como las páginas nacen en cero, el byte 11 de nuestro bloque es un \0. Eso es lo único que hace que el printf("%s") del consumidor termine la cadena en algún lado. El productor nunca escribe un terminador — funciona por casualidad.

    

  


  

    3 · mmap void *mmap(void *addr, size_t len, int prot, int flags, int fd, off_t off)
    

      
El corazón de la práctica. Crea un VMA (Virtual Memory Area) en el proceso: un rango de direcciones virtuales asociado al objeto.

      
ptr = mmap( 0,            // NULL = el kernel elige dirección
              4096,           // longitud
              PROT_WRITE,     // protección: PROT_READ|WRITE|EXEC|NONE
              MAP_SHARED,     // ¿compartido o copia privada?
              fd, 0 );        // fd y offset

      
    
        
  • PROT_READ | PROT_WRITE — permisos del mapeo. Si abrís con O_RDONLY pero mapearas PROT_WRITE, el kernel te da EACCES: los permisos del fd recortan los del mapeo.
    • 
        
  • MAP_SHARED — las escrituras van a la página física compartida. MAP_PRIVATE haría copy-on-write y rompería la comunicación.
    • 
        
  • MAP_ANONYMOUS — memoria sin backing file. No es lo que necesitamos.
    • 
        
  • MAP_FIXED — fuerza la dirección. Nunca lo uses: pisa tus propias variables.
    • 
      

      
Lo importante: el productor y el consumidor reciben direcciones virtuales distintas (el kernel elige libre) pero apuntan a la misma página física. Por eso el consumidor no puede hacer aritmética de punteros sobre el offset del productor: los offsets sí coinciden, las direcciones no.

    

  


  

    4 · shm_unlink int shm_unlink(const char *name)
    

      
Borra el nombre del filesystem. Equivale a unlink() en archivos normales.

      
shm_unlink( "OS" );   // /dev/shm/OS desaparece

      
    
        
  • Un proceso que ya lo tiene mapeado seguí viendo los datos intactos hasta que termine. Es el mismo modelo de Unix: borrar un archivo abierto no lo invalida.
    • 
        
  • La página física se libera cuando el último mapeo o fd se cierra.
    • 
        
  • Por eso el shm_unlink va en el consumidor y no en el productor: si el productor lo hiciera, el consumidor ya no podría abrir el objeto por nombre.
    • 
      

      
Bug grave si no lo hacés: el objeto sobrevive al exit de ambos procesos. La próxima ejecución del productor reabre el mismo bloque con datos viejos. Se limpia a mano con rm /dev/shm/OS o shm_unlink("OS") al inicio.

    

  


  

    5 · sprintf / strlen / printf funciones de biblioteca, NO son syscalls
    

      
Estas tres son funciones de biblioteca de C, no llamadas al sistema. Se ejecutan enteras en user mode, sin trap al kernel.

      
    
        
  • sprintf(ptr, "%s", msg) — memcpy puro: copia bytes hasta el \0 de msg. Escribe solo los 5 bytes de "Hello". No toca la memoria del kernel.
    • 
        
  • strlen(msg) — recorre la cadena contando bytes. No es O(1) aunque el hardware lo parezca: hace un barrido real de memoria.
    • 
        
  • ptr += strlen(msg) — simple aritmética de punteros en un registro. Cero syscalls.
    • 
      

      
El bug del ptr +=: no deja ni un espacio ni un \0 entre las dos cadenas. El resultado en RAM es HelloWorld!, no Hello World!. Para el ASCII que se nota poco, pero el dato está corrupto igual.

Problemas y buenas prácticas

  

    
🔴
Sin sincronización
El problema central. Sin sem_open/sem_wait el consumidor puede leer antes, durante o después de la escritura.

    
🟠
Dos cadenas pegadas
ptr += strlen() no deja separador. Resultado: HelloWorld!. Debería ser ptr += strlen(m) + 1 o escribir "Hello ".

    
🟠
Fuga de /dev/shm
Si el consumidor no corre, el objeto queda huérfano para siempre. df -h /dev/shm para verificar.

    
🟡
No se unmapea
Faltan munmap(ptr, SIZE) y close(fd). El kernel limpia al morir el proceso, pero es mala práctica y lo usan los recolectores.

    
🟡
SIZE duplicado como constante
4096 está hardcodeado en los dos archivos. Si cambiás uno y no el otro, mmap falla o leés de más.

    
🟡
Nombre fijo
"OS" es global en el sistema: dos alumnos en la misma máquina colisionan. Usá "/mi_practica3_<pid>".

Compilar y ejecutar

  

    
gcc -o product  producer.c -lrtEn glibc moderno -lrt es opcional; si te da undefined reference to shm_open, ponelo.

    
gcc -o consumid consumidor.c -lrtEl nombre del binario no importa, pero el del objeto ("OS") sí.

    
./productCrea el objeto y escribe. No imprime nada.

    
./consumidLee e imprime HelloWorld!, después borra el objeto.

    
./consumid && ./productOrden inverso → shm_open falla con No such file or directory. Exactamente lo que chequea el perror.

    
ls -l /dev/shm/Mientras el objeto está vivo, aparece un archivo de 4096 bytes ahí.

    
rm /dev/shm/OSLimpieza manual si un run anterior quedó a medias.

  


  

    Resumen en una frase: shm_open crea el archivo, ftruncate le da tamaño, mmap lo conecta a tu memoria, y como ambos mapean el mismo objeto con MAP_SHARED, el uno escribe en la RAM del otro. Todo lo demás — permisos, orden de arranque, terminadores de cadena — es la parte que el código original no resuelve.

🌱
copy-on-write nunca se separó
El kernel copió las page tables cinco veces y ningún proceso escribió jamás una página compartida. Todo ese trabajo fue para nada.

    
🔗
el fd table se comparte
Padre e hijo no copian el descriptor: apuntan al mismo struct file de stdout. Por eso la palabra del hijo aparece en la misma terminal.

    
💣
el buffer se hereda igual
Si el padre tuviera texto sin lavar al hacer fork, los dos hijos lo volcarían duplicado. Mirá el toggle ☠.
